Identity & Access Management

IAM is the framework of policies, processes, and technologies that ensures the right principals have the right access to the right resources at the right time for the right reasons.

Core Concepts
  • Identity: The digital representation of an entity (user, service, device) that can be authenticated.
  • Principal: The actor requesting access — typically a user, machine, or service, backed by an identity.
  • Authentication (AuthN): The process of proving who you are, usually via credentials.
  • Authorization (AuthZ): Determining what an authenticated principal is allowed to do.
  • Credential: The secret used to verify an identity (password, API key, certificate, token).
  • Claim: A statement about an identity (e.g., role, email, group) carried in tokens to make authorization decisions.
  • Policy / Entitlement: The rule or grant that binds a principal to specific actions on specific resources.
  • Session: The state maintained once a principal has authenticated, so access checks don't repeat AuthN.
Actors & Entities
  • Identity Provider (IdP): The trusted party that authenticates users and issues tokens/assertions (e.g., Entra ID, Okta, Auth0).
  • Relying Party (RP) / Service Provider (SP): The application that trusts the IdP and consumes identity information to grant access.
  • Directory: The authoritative store of identities, groups, and attributes (e.g., Active Directory/Entra ID, LDAP).
  • Trust Relationship: The configured agreement that lets an RP rely on an IdP's assertions (federation trust).
Access Models
  • RBAC (Role-Based Access Control): Permissions are assigned to roles, which are then assigned to principals. Simple and coarse-grained; most common model.
  • ABAC (Attribute-Based Access Control): Access decisions are made dynamically using policies evaluated against subject, resource, and context attributes. Fine-grained and flexible.
  • Federated Identity: Identities are held and verified by an external identity provider (IdP) and trusted across organizations or domains, enabling SSO.
  • Discretionary Access Control (DAC): The resource owner decides who gets access (e.g., file-level NTFS permissions).
  • Mandatory Access Control (MAC): Access is governed by system-wide security labels that principals cannot override.
Token Strategies
  • Opaque tokens: Validated via introspection; easy to revoke immediately. Good for high-security, short-lived, centralized scenarios.
  • JWT: Self-contained and verifiable offline; good for distributed decoupled microservices.
  • Trade-off: JWTs cannot be revoked easily until expiry — shorten lifetime or use a revocation/denylist for sensitive operations.
  • Bearer token risk: Treat tokens as secrets; minimize their exposure surface (client storage, logs, referrers).
Policies & Practices
  • Least Privilege: Grant principals only the minimum permissions required to perform their function.
  • Defense in Depth: Layer multiple independent security controls so that no single failure compromises access.
  • Separation of Duties: Fragile or sensitive actions require two or more principals to prevent abuse of power.
  • Zero Trust: Never trust, always verify — verify explicitly, grant least access, and assume breach with continuous verification.
  • Conditional Access: Evaluate context (device posture, location, sign-in risk) before granting access instead of trusting the credential alone.
  • Identity Lifecycle: Provision, manage, and deprovision identities as people join, change, and leave the organization.
Privileged Access
  • Privileged Access Management (PAM): Special controls and workflows around high-privilege accounts (brokering, just-in-time access).
  • Just-in-Time (JIT) access: Elevate privileges on demand for a limited duration, then automatically revoke.
  • Break-glass accounts: Emergency high-privilege accounts held for crises; require strict controls, monitoring, and approval on use.
  • Standing access vs JIT: Prefer time-bound, approved elevation over permanent high-privilege assignments.
Permission Evaluation
  • Deny overrides allow: An explicit deny always wins over any allow — enforce this when combining policies.
  • Effective permissions: The final access decision is the result of merging all applicable policies from identity-based and resource-based grants.
  • Evaluation order: Union all allows, subtract explicit denys, then apply any restrictions (conditions, scopes).
  • Ownership: Resource owners can often delegate access within their owned scope (DAC behavior layered on RBAC).
Identity Governance
  • Access reviews: Periodically recertify that principals still need their granted access.
  • Attestation: Formal sign-off that access assignments are correct and compliant.
  • Entitlements: The catalog of manageable access packages (group membership, roles, apps) a user can be granted.
  • Deprovisioning: Remove access promptly on offboarding or role change to close orphaned-account risks.
  • Audit log: Record who accessed what and when for forensics, compliance, and anomaly detection.
Common Technologies
  • SSO (Single Sign-On): A single authentication grants access to multiple applications without re-authenticating.
  • MFA (Multi-Factor Authentication): Requires two or more factors (something you know, have, or are) to verify identity.
  • SCIM (System for Cross-domain Identity Management): Standard protocol for automating identity provisioning and deprovisioning between systems.
  • SAML / OIDC / JWT: Assertion and token formats used to carry identity and authorization data between parties.
  • Passwordless: Authentication using passkeys, FIDO2/WebAuthn, or one-time codes instead of static passwords.

Security

OAuth 2.0

OAuth 2.0 is an authorization framework that allows third-party applications to obtain limited access to a user's resources without exposing their credentials. It provides a way for applications to interact with each other on behalf of the user without needing to directly access their password

Key Concepts
  • Resource Owner: The user who owns the data and can grant access to it.
  • Client: The application requesting access to the user's resources on their behalf.
  • Resource Server: The server hosting the protected resources. It verifies the access tokens and serves the requested resources.
  • Authorization Server: The server issuing access tokens to the client after authenticating the user and obtaining their authorization.
  • Authorization Grant: The method by which the client obtains an access token. There are several types of grants (flows).
  • Access Token: A token that the client uses to make authenticated requests on behalf of the resource owner.
  • Refresh Token: A token used to obtain a new access token without requiring the user to re-authenticate.
Key JWT Claims
  • iss (Issuer): The issuer is the entity that created and signed the JWT (authorization server or IdP).
  • aud (Audience): The audience is the intended recipient of the token (API or service that will consume it).
  • sub (Subject): Represents the user or entity to which the token refers. It is a unique identifier for the user in the context of the issuer. (Excluded in client credentials flow)
  • scope (Scopes): Lists the scopes or permissions associated with the token (what actions the token can perform).
Authorization Flow Grants
  • Authorization Code Grant (+ PKCE)
    • Used by web and mobile applications to obtain access tokens securely via the backend server. PKCE is required for public clients (SPAs, mobile).
    • Advantages: Secure because the access token is not exposed to the user agent and is exchanged server-to-server.
  • Implicit Grant (deprecated)
    • Previously used by SPAs and public clients; the access token was returned directly in the redirect. Now superseded by Authorization Code + PKCE.
    • Disadvantages: Token exposed in URL/history; vulnerable to interception. Do not use for new implementations.
  • Resource Owner Password Credentials Grant
    • Used when the client is highly trusted by the resource owner, such as first-party clients.
    • Advantages: Direct and straightforward for trusted clients.
    • Disadvantages: Not recommended for third-party clients due to security concerns of exposing user credentials to the client.
  • Client Credentials Grant
    • Used for machine-to-machine (M2M) applications where no user is involved.
    • Advantages: Suitable for server-to-server communication.
PKCE (Proof Key for Code Exchange)

An extension to the Authorization Code Grant that protects public clients (SPAs, mobile apps) against authorization code interception.

  • code_verifier: A high-entropy random string generated by the client and kept secret on the client.
  • code_challenge: A transformed version of the code_verifier sent with the authorization request. Usually the SHA-256 hash (method S256).
  • Verification: At the token endpoint the client sends the code_verifier, and the authorization server checks it against the code_challenge before issuing tokens.
OpenID Connect (OIDC)

OIDC is an identity layer built on top of the OAuth 2.0 protocol. It adds authentication on top of the authorization, allowing clients to verify the identity of the user via an ID Token while also obtaining basic profile information.

Key Concepts
  • ID Token: A JWT issued by the authorization server that contains claims about the authenticated user (such as sub, name, and email). It is the core addition of OIDC over plain OAuth 2.0.
  • UserInfo Endpoint: A protected endpoint the client can call with an access token to retrieve additional claims about the user.
  • Discovery Endpoint: A well-known URL (.well-known/openid-configuration) that exposes the authorization server's metadata, scopes, and endpoints.
Claims
  • id_token: The signed JWT representing the authentication result and user claims.
  • openid: The required scope for an OIDC request; signals the client intends to authenticate the user.
  • profile / email / phone: Optional scopes that grant access to additional user claims via the UserInfo endpoint.
Token Types
  • Structured tokens (JWT): Self-contained, verifiable offline via signature; carry claims. Good for distributed APIs, but harder to revoke before expiry.
  • Opaque/reference tokens: Random strings with no meaning by themselves; validated server-side by the authorization server.
  • Introspection Endpoint (RFC 7662): Used by a resource server to validate an opaque token and retrieve its metadata (active, scope, client_id).
  • Bearer tokens: Whoever holds the token can use it. Must be protected in transit (TLS) and at rest; consider short lifetimes and rotation.
Token Validation
  • Signature: Always verify the token signature against the issuer's keys before trusting any claim.
  • exp (Expiration): The token is invalid after this timestamp. Always enforce it.
  • nbf (Not Before): The token is not valid before this timestamp.
  • iat (Issued At): When the token was issued; reject tokens issued too long ago / in the future.
  • iss & aud: Validate the issuer matches the expected IdP and the audience matches your client/resource.
JWT Security
  • Algorithm confusion: Never accept tokens signed with an algorithm you did not expect. RS256/ES256 use public/private keys; HS256 uses a shared secret — confusing them lets attackers forge tokens.
  • Reject alg=none: Do not accept unsigned tokens or a downgrade to none.
  • Short lifetimes: Issue short-lived tokens and rely on refresh token rotation instead of long expirations.
  • Rotation: Rotate refresh tokens on each use; detect if an old rotatee is replayed (potential theft).
  • Don't put secrets in tokens: JWTs are base64, not encrypted by default — do not store sensitive data unless using JWE.
Asp.Net Core

Usually an api has a cookie scheme as the default authenticationSchema with external providers as secondary.

When triggering an ChallengeAsync on the external provider, it will prompt an redirect. After a successfully login the external provider will redirect the user back to the original api where the api will perform a SignInAsync based on the user received from the external provider. That will create the cookie.

Key Apis
  • HttpContext.User: Represents the current user’s identity and claims.
  • AuthenticateAsync: This method is used to validate and authenticate the user's credentials or token, but without enforcing any required login or redirect
  • ChallengeAsync: This method is used to enforce authentication. When a challenge is issued, it triggers the authentication system to redirect the user to a login page or prompt them for credentials (depending on the authentication scheme). It is a way to tell the system that the user must be authenticated before proceeding.
  • SignInAsync: Signs in a user, creating an authentication ticket (e.g., generating a cookie or token).
  • SignOutAsync: Signs the user out, invalidating the authentication ticket (e.g., deleting the cookie or token).
Common Web Attacks
  • CSRF (Cross-Site Request Forgery): Attacker tricks a user's browser into making authenticated requests. Mitigate with anti-forgery tokens and SameSite cookies.
  • XSS (Cross-Site Scripting): Attacker injects scripts executed in the victim's browser. Mitigate with output encoding and CSP.
  • SQL Injection: Malicious SQL embedded in input. Mitigate with parameterized queries, never string concatenation.
  • SSRF (Server-Side Request Forgery): Attacker makes the server fetch arbitrary URLs. Mitigate by whitelisting destinations and validating URLs.
  • Open Redirect: Attackers abuse lax redirect_uri validation to redirect users to phishing sites. Always validate redirect_uri against a registered allowlist.
  • Token replay/theft: Stolen access tokens replayed to the API. Mitigate with short lifetimes, TLS, and refresh token rotation.
Defensive Controls
  • Security headers: Content-Security-Policy (CSP), HTTP Strict Transport Security (HSTS), X-Frame-Options, X-Content-Type-Options.
  • Cookie flags: HttpOnly (no JS access), Secure (HTTPS only), SameSite (mitigates CSRF).
  • CORS: Restrict allowed origins to known domains; never use the wildcard with credentials.
  • Rate limiting: Protect login and token endpoints against brute-force and credential-stuffing attacks.
  • TLS: Encrypt all traffic in transit (HTTPS). Never send tokens or credentials over plain HTTP.
Passwords & Secrets
  • Hashing: Store password hashes only, using adaptive algorithms: Argon2id, scrypt, bcrypt, PBKDF2. Never plaintext or reversible hashes (MD5/SHA1).
  • Salting: Use a unique random salt (or the algorithm's built-in salt) per password to defeat rainbow tables.
  • Secrets management: Keep client secrets, keys, and connection strings out of source code; use a vault (e.g., Azure Key Vault, HashiCorp Vault) and rotate on a schedule.

Cryptography

JWT Structure

A JWT is three base64url-encoded segments separated by dots: header.payload.signature.

  • Header: Metadata, e.g. {"alg":"RS256","typ":"JWT","kid":"key-1"}. The kid tells verifiers which key to fetch for validation.
  • Payload: The claims. Base64url-encoded, not encrypted — anyone can read it. Treat contents as public information.
  • Signature: Cryptographically binds the header and payload so tampering can be detected.
JWS (JSON Web Signature)

Signing provides integrity and authenticity, not confidentiality. A recipient can verify the claims came from the signer and were not altered.

  • HMAC (e.g. HS256): Symmetric — the same shared secret signs and verifies. Simple, but the secret must be guarded by every verifier.
  • Asymmetric (e.g. RS256, ES256): The private key signs, the public key verifies. Preferred for distributed systems and public clients.
  • Signing input: Always the exact string base64url(header) + "." + base64url(payload).
JWS Code Sample (C#)

Signing a JWT with RSA-SHA256 (RS256) using the .NET standard library:

using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Security.Cryptography;
using Microsoft.IdentityModel.Tokens;

using var rsa = RSA.Create(2048);
var privateKey = new RsaSecurityKey(rsa);
var signingCredentials =
    new SigningCredentials(privateKey, SecurityAlgorithms.RsaSha256);

var token = new JwtSecurityToken(
    issuer: "https://auth.example.com",
    audience: "api.example.com",
    claims: new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub, "user-42"),
        new Claim("role", "admin")
    },
    notBefore: DateTime.UtcNow,
    expires: DateTime.UtcNow.AddMinutes(15),
    signingCredentials: signingCredentials);

var handler = new JwtSecurityTokenHandler();
string jwt = handler.WriteToken(token);
Console.WriteLine(jwt); // header.payload.signature

Verifying the signature and validating the standard claims:

using System.IdentityModel.Tokens.Jwt;
using Microsoft.IdentityModel.Tokens;

var publicKey = new RsaSecurityKey(rsa); // public part of the same key
var parameters = new TokenValidationParameters
{
    ValidateIssuer = true,
    ValidIssuer = "https://auth.example.com",
    ValidateAudience = true,
    ValidAudience = "api.example.com",
    ValidateLifetime = true, // enforces exp / nbf
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = publicKey
};

var principal = new JwtSecurityTokenHandler()
    .ValidateToken(jwt, parameters, out _);
Console.WriteLine(principal.Identity?.IsAuthenticated); // True

Note: verifying with the private key (or with HS256 and someone else's secret) would be a security flaw — always verify with the expected public key.

JWE (JSON Web Encryption)

JWE adds confidentiality on top of signing: the payload is encrypted and unreadable without the recipient's key.

  • Content Encryption Key (CEK): A random symmetric key that encrypts the payload (e.g. A256GCM, A128CBC-HS256).
  • Key management: The CEK is wrapped with the recipient's public key (alg: RSA-OAEP) or derived from a shared secret (alg: dir).
  • Header: Carries alg and enc, e.g. {"alg":"RSA-OAEP-256","enc":"A256GCM"}.
  • When to use JWE: Only for sensitive claim content (PII, internal identifiers). For typical authorization, JWS is enough — encryption adds complexity and prevents some audiences from reading claims.
JWE Code Sample (C#)

Encrypting the claims payload with RSA-OAEP-256 / A256GCM:

using System.Security.Cryptography;
using Microsoft.IdentityModel.Tokens;

var recipientPublicKey = new RsaSecurityKey(rsa); // recipient's key
var encryptedCreds = new EncryptingCredentials(
    recipientPublicKey,
    SecurityAlgorithms.RsaOaepKeyWrap,
    SecurityAlgorithms.Aes256Gcm);

var token = new JwtSecurityToken(
    issuer: "https://auth.example.com",
    audience: "api.example.com",
    claims: new[]
    {
        new Claim("email", "user@example.com"),     // now confidential
        new Claim("ssn", "123-45-6789")
    },
    expires: DateTime.UtcNow.AddMinutes(15),
    signingCredentials: signingCredentials,        // JWS layer
    encryptingCredentials: encryptedCreds);        // JWE layer (Nested JWT)

string jwt = new JwtSecurityTokenHandler().WriteToken(token);
Console.WriteLine(jwt); // encrypted: header.encKey.iv.ciphertext.tag

Decrypting with the recipient's private key and validating claims:

using Microsoft.IdentityModel.Tokens;

var recipientPrivateKey = new RsaSecurityKey(rsa); // recipient's private key
var parameters = new TokenValidationParameters
{
    ValidateIssuer = true,
    ValidIssuer = "https://auth.example.com",
    ValidateAudience = true,
    ValidAudience = "api.example.com",
    ValidateLifetime = true,
    IssuerSigningKey = new RsaSecurityKey(rsa),      // for the inner JWS
    TokenDecryptionKey = recipientPrivateKey,        // for the JWE layer
    ValidateIssuerSigningKey = true
};

var principal = new JwtSecurityTokenHandler()
    .ValidateToken(jwt, parameters, out SecureToken validated);
Console.WriteLine(((JwtSecurityToken)validated).Claims);
SAML2 Assertion & XML Signature

A SAML2 <saml:Assertion> is signed by wrapping it in an XML Signature (ds:Signature) per XMLDSig. The assertion text itself is not encrypted by default — it is signed for authenticity and integrity.

  • SignedInfo: The part that gets signed. Contains CanonicalizationMethod (c14n), SignatureMethod (usually RSA-SHA256), and one or more Reference entries.
  • Reference: Points at the signed element (e.g. #assertion-id) and carries DigestMethod (SHA-256) plus DigestValue — a hash of the canonicalized assertion content.
  • KeyInfo: Usually embeds the signer's X.509 certificate so the relying party can bind it to a trusted trust anchor.
  • Verification flow: (1) re-canonicalize SignedInfo, (2) verify the signature in SignatureValue against it with the signer's public key, (3) re-canonicalize and digest the referenced assertion, (4) confirm it matches DigestValue.
  • Canonicalization matters: Any whitespace or attribute-order change alters the digest — both sides must canonicalize identically (C14N).
SAML2 Code Sample (C#)

Signing an XML assertion with RSA-SHA256 using SignedXml:

using System.Security.Cryptography;
using System.Security.Cryptography.Xml;
using System.Xml;

var assertion = new XmlDocument { PreserveWhitespace = false };
assertion.LoadXml("""
<saml:Assertion xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
                ID="assertion-id" IssueInstant="2026-09-08T12:00:00Z">
  <saml:Issuer>https://idp.example.com</saml:Issuer>
  <saml:Subject>
    <saml:NameID>alice@example.com</saml:NameID>
  </saml:Subject>
  <saml:AuthnStatement AuthnInstant="2026-09-08T12:00:00Z">
    <saml:AuthnContext>
      <saml:AuthnContextClassRef>urn:oasis:names:tc:SAML:2.0:ac:classes:Password
      </saml:AuthnContextClassRef>
    </saml:AuthnContext>
  </saml:AuthnStatement>
</saml:Assertion>
""");

var signedXml = new SignedXml(assertion);
using var rsa = RSA.Create(2048);
signedXml.SigningKey = rsa;
signedXml.SignedInfo.CanonicalizationMethod =
    SignedXml.XmlDsigCanonicalizationUrl;                            // c14n
signedXml.SignedInfo.SignatureMethod =
    SignedXml.XmlDsigRSASHA256Url;                                   // RSA-SHA256

var reference = new Reference("#assertion-id");                       // -> Reference node
reference.DigestMethod =
    SecurityAlgorithms.Sha256Digest;                                 // DigestMethod
reference.AddTransform(new XmlDsigC14NTransform());                  // canonicalize before hashing
signedXml.AddReference(reference);

var keyInfo = new KeyInfo();                                          // KeyInfo -> certificate
keyInfo.AddClause(new KeyInfoX509Data(certificate));
signedXml.KeyInfo = keyInfo;

signedXml.ComputeSignature();
var signature = signedXml.GetXml();

var s = assertion.DocumentElement!;
s.AppendChild(assertion.ImportNode(signature, true));                 // ds:Signature child

Verifying the signature and digest of a received assertion:

using System.Security.Cryptography.Xml;
using System.Xml;

var received = new XmlDocument { PreserveWhitespace = false };
received.LoadXml(signedXmlText);

var ns = new XmlNamespaceManager(received.NameTable);
ns.AddNamespace("ds", "http://www.w3.org/2000/09/xmldsig#");
var sigNode = received.SelectSingleNode("//ds:Signature", ns)!;

var signedXml = new SignedXml(received);
signedXml.LoadXml((XmlElement)sigNode);

bool sigValid = signedXml.CheckSignature(rsa);          // 1+2: re-canonicalize SignedInfo,
                                                        // verify SignatureValue
Console.WriteLine($"Signature valid: {sigValid}");

foreach (Reference reference in signedXml.SignedInfo.References)
{
    bool digest = reference.CheckDigest();               // 3+4: digest of signed content
    Console.WriteLine($"Digest for {reference.Uri}: {digest}");
}

In production, the public key comes from the trusted IdP's certificate (from KeyInfo or a pre-shared metadata document), not from within the message itself.
